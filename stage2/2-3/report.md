# 子代理 vs 無頭模式（claude -p）：各適合什麼情境

1. 兩者的定位不一樣：子代理在**一個 session 裡**分工，每個子代理有「自己的 context window、system prompt、工具權限」（note-1.md 第一節）；`claude -p` 則是「沒有互動式介面，跑一次 prompt 就結束」的執行方式（note-2.md 第一節）。
2. 子代理最主要的好處是**保護主 context**：中間的雜訊留在子代理那邊，主對話「只拿到最後的結論」（note-1.md 第二節）。
3. 所以子代理適合三類工作：大量搜尋只要結論、彼此獨立可以平行的工作、code review 這類專業分工；經驗法則是「調查會讓主 context 多出大約 1,000 tokens 以上」就交給子代理（note-1.md）。
4. 子代理不適合很小的查詢，也不適合緊密耦合、需要來回溝通的工作，因為每次啟動都有固定開銷，而且它「看不到主對話的歷史」（note-1.md 第三節）。
5. 無頭模式適合**沒有人在旁邊的自動化**：CI/CD（自動審查 PR、分析測試失敗原因）、cron／schtasks 排程、pre-commit、批次處理，以及 `cat error.log | claude -p` 這種 pipe 串接（note-2.md 第二節）。
6. 無頭模式可以用 `--output-format json` 和 `--json-schema` 輸出結構化結果，讓下游程式直接解析，也能靠結束代碼判斷成敗（note-2.md）。
7. 無頭模式不適合探索式的工作，因為「`-p` 執行中沒辦法問你」；權限要用 `--allowedTools` 收到最小，成本要用 `--max-turns`、`--max-budget-usd` 設上限（note-2.md 第三節）。
8. 兩邊共同的風險是成本：平行派 N 個子代理，消耗大約是 N 倍（note-1.md 第四節）；無頭模式的批次則可能在沒人看的時候燒掉大量 token（note-2.md 第三節）。
9. 兩者可以搭配使用：用 `claude -p` 在 CI 裡觸發任務，任務裡面再派子代理平行搜尋，這樣同時得到自動化和 context 隔離（綜合兩份筆記）。
10. 結論：**要在對話中分擔工作、保護 context，用子代理；要讓工作在沒人在場時可重複執行、接進腳本，用 `claude -p`**。另外，無頭模式要驗證實際產出，因為有「exit 0 但 commit 根本不存在」的案例（note-2.md）。
